## 2. Контракт створення і CP-01

### Request, response та entity

`POST /api/incidents` приймає JSON через окремий [CreateIncidentRequest](../src/SecureLab.Api/Presentation/Contracts/IncidentRequests.cs). Entity `Incident` не використовується як модель запиту. Успіх: `201 Created`, заголовок `Location: /api/incidents/{id}` та [CreatedIncidentResponse](../src/SecureLab.Api/Presentation/Contracts/IncidentResponses.cs).

| Поле запиту | Правило | Порушення |
|---|---|---|
| title | Обов'язковий після Trim; не більше 160 символів у надісланому значенні до Trim | 400, errors.title |
| description | Обов'язковий після Trim; не більше 4000 символів до Trim | 400, errors.description |
| severity | Enum.TryParse разом із Enum.IsDefined; Low, Medium, High, Critical | 400, errors.severity |
| occurredAtUtc | Обов'язковий DateTimeOffset; не пізніше now + 5 хвилин; now фіксується один раз на початку обробника | 400, errors.occurredAtUtc |

Title і Description нормалізуються через Trim по одному разу. Довжина до Trim перевіряється на початковому значенні. Для High/Critical опис після Trim має містити щонайменше 40 символів; 39 дає 400 з ключем description, 40 приймається.

`Enum.TryParse` сам по собі приймає числові рядки. `Enum.IsDefined` додатково перевіряє наявність значення в enum: рядок `"7"` відхиляється.

Момент `2026-09-01T13:00:00+03:00` приймається й перед записом нормалізується через ToUniversalTime у `2026-09-01T10:00:00Z`. Зміщення саме по собі не є помилкою.

### Предметний конфлікт

Після базової та cross-field валідації перевіряється наявність інциденту з тим самим нормалізованим title та статусом, відмінним від Closed. Збіг у New, Triaged, InProgress або Resolved повертає 409 Problem Details. Порівняння враховує регістр. Closed дозволяє повторне створення.

Реалізація: [Lab02Endpoints.CreateIncidentAsync](../src/SecureLab.Api/Scaffolding/Lab02Endpoints.cs).

### Серверні поля й безпечні відповіді

Id генерується сервером; OwnerUserId береться зі сталого навчального контексту Alice; Status дорівнює New. CreatedAtUtc і UpdatedAtUtc отримують один і той самий серверний now. Власник із перевіреної особи буде предметом наступної ЛР; поточний код не реалізує автентифікацію.

Зайві JSON-поля id, ownerUserId, status, createdAtUtc та updatedAtUtc не входять у request DTO й ігноруються. Перевірка надсилала чужий ownerUserId, статус Closed і підставний id: створено новий id, статус New, власник Alice; службові часи задані сервером. Окремий response DTO містить лише id, title, description, severity, status, occurredAtUtc та createdAtUtc.

Маршрут CP-01: JSON → CreateIncidentRequest → перевірки полів → cross-field правило → перевірка конфлікту → створення Incident → збереження → CreatedIncidentResponse. Неприпустимі поля дають 400 до запитів перевірки конфлікту та запису entity. HTML select не замінює ці перевірки, оскільки JSON можна надіслати напряму.

400, 404 та 409 мають Content-Type application/problem+json, title і status. У 400 є errors з ключами полів, у 404/409 є detail. Перевірені відповіді не містять stack trace, SQL, connection string або внутрішніх назв компонентів.

Докази: [T-01/CP-01](evidence/t01-contract.txt), [T-02](evidence/t02-contract.txt), [T-03](evidence/t03-contract.txt), [T-06](evidence/t06-contract.txt), [T-09](evidence/t09-contract.txt).

## 3. Security-сценарій і CP-02/CP-03

### Контекст і гіпотеза

Локальний GET /api/incidents/search отримує недовірені q та sortBy із query string. У початковому scaffold вони приєднувались до SQL-тексту, тому могли змінити структуру запиту. Усі перевірки виконано лише на localhost у Development зі штучними даними PostgreSQL. Сторонні системи не перевірялися.

### Стан до і CP-02

Vulnerable state: `dda77df233f9d3f460e6d6e2382069b3bcfbfe22`. Точка: [Lab02Endpoints.MapLab02Endpoints у vulnerable commit](https://github.com/dimtor02/prykladne_prohramuvannya/blob/dda77df233f9d3f460e6d6e2382069b3bcfbfe22/src/SecureLab.Api/Scaffolding/Lab02Endpoints.cs#L13). Це посилання стане доступним на GitHub після push студентом відповідної історії; локальний commit уже створено.

У цьому стані рядок 18 допускав довільний sortBy, рядки 20-21 з'єднували q і фрагмент сортування з SQL, рядок 22 передавав готовий текст у FromSqlRaw. Маршрут: query string → параметри q/sortBy handler → складання SQL → FromSqlRaw → PostgreSQL → JSON.

### Виправлення і CP-03

Пошук перенесено до [IncidentQueries.SearchAsync](../src/SecureLab.Api/Application/Incidents/IncidentQueries.cs). FromSqlRaw і конкатенацію SQL усунуто. EF.Functions.ILike виконує нечутливий до регістру пошук у Title або Description; pattern передається параметром EF Core. Окремо екрануються backslash, %, _ саме в такому порядку, після чого додаються зовнішні wildcard для substring. Це зберігає буквальне значення введених метасимволів; параметризація сама по собі не вимикає їхню LIKE-семантику.

У [Lab02Endpoints.SearchIncidentsAsync](../src/SecureLab.Api/Scaffolding/Lab02Endpoints.cs) невідомий sortBy дає 400 з errors.sortBy до виконання query. Відсутнє або порожнє значення обирає createdAtUtc. Дозволені лише createdAtUtc, severity та status. Значення параметризуються, а SQL-структура сортування обирається наперед заданими типізованими LINQ-виразами; ім'я колонки не підставляється як параметр чи довільний текст.

- createdAtUtc: новіші записи першими.
- severity: Critical → High → Medium → Low, через явні ранги.
- status: New → Triaged → InProgress → Resolved → Closed, через явні ранги.
- Після основного сортування: ThenBy(Id), потім Take(50), потім response DTO-проєкція.

Той самий сценарій C після виправлення дав 200 та []. Автоматичний S-02 додатково перевірив точну порожню множину. Позитивні тести підтвердили USB, нечутливість до регістру, апострофи, пошук буквальних %, _, backslash у Title і Description з виключенням контрольного невідповідного запису. Перевірки на 60 власних записах підтвердили кожний порядок, tie-break за Id і вибір перших 50 після сортування.

Журнал п'яти повторних HTTP-запитів показав окремі параметри EF: [доказ відокремлення SQL і даних](evidence/sql-separation.txt). Повний SQL, рядки підключення, credentials та дампи до звіту не включені.

Огляд A-01: [таблиця raw-SQL місць і висновків](evidence/a01-data-access.md). У пошуку немає raw-SQL; сталий reset із фіксованими таблицями не використовує HTTP-введення. Додатковий збіг у тесті є складанням URL, а не SQL.

Залишкові ризики: це виправлення не додає автентифікацію/авторизацію, повноцінну пагінацію, обмеження складності всіх запитів чи production-політику журналювання. Take(50) обмежує кількість результатів, але не обов'язково вартість пошуку.

## 5. Обмеження і висновок

Реалізовано та перевірено контракт створення для рівня «Добре», безпечний пошук і allowlist сортування. Контрольний ввід більше не змінює логіку вибірки, а легітимні апострофи працюють. Проведено A-01 і фінальні технічні перевірки. Завершення Git-оформлення та подання залишається за студентом.

AnyAsync перед SaveChangesAsync не гарантує унікальності за одночасних запитів: між перевіркою та записом інший запит може створити збіг. Для гарантії потрібне узгоджене обмеження БД або транзакційне рішення. За методикою ЛР2 нова migration/унікальний індекс не додаються.

Захист від overposting не замінює автентифікацію та авторизацію. Контрактні тести використовують синтаксично правильний JSON; поведінка стартового конвеєра на пошкодженому JSON цим прогоном не перевірялася.
